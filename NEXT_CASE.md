# NEXT_CASE.md

## How I Will Add My Next Project to My Portfolio

This document is my plan for adding the next case study to my portfolio. It keeps my portfolio simple, honest and consistent.



I am an aspiring Data Analyst and Business Analyst. I am building a foundation in SQL, Python, Excel and Power BI. My portfolio has four pages: Home, Projects / Case Studies, About Me and Contact. Every new case study goes on the Projects / Case Studies page.



My goal is to help recruiters and hiring managers see what I can do, so they can contact me about entry-level roles.

---

## The Rules I Follow

- I only write what I actually did.
- I only report results I can show with evidence.
- If something is not finished, I say so.
- If something did not work, I say what happened and what I learned.
- I do not claim skills I have not used in the project.
- I write in plain English and keep sentences short.

---

## The Three Sections

Every case study uses the same three sections. This keeps my portfolio easy to read.

### 1. Problem

What problem did the project address?

- Say what the problem or question was.
- Say why I took on this project.
- Keep it to a few sentences.
- If it was a learning project, say that. That is honest and fine.

### 2. What I Did

What tools and steps did I use?

- List the tools I really used (for example: Python, SQL, Excel, Power BI, Git).
- Describe the steps in the order I did them.
- Explain any technical term in simple words.
- Mention the key decisions I made and why.
- Mention problems I ran into and how I handled them.

### 3. What Came Out of It

What was the result and what did I learn?

- State the result using only facts I can prove (for example: test results, a working output, a finished dashboard).
- Say clearly what is finished and what is not.
- Share what I learned, including what I am still improving.
- Do not add numbers, impact or business results I did not measure.

## Steps for Adding a New Case Study

### Step 1: Finish and check the project

- Make sure the project works as I plan to describe it.
- Run it again. Check that the results I want to quote are real.
- Write down anything that is incomplete.

### Step 2: Collect my notes

Before writing, I write short answers to these questions:

- What was the project?
- Why did I build it?
- What tools did I use?
- What decisions did I make?
- What problems did I face?
- What was the result?
- What did I learn?
- What is still unfinished or could be better?

I only use these notes when I write the case study.

### Step 3: Gather evidence

For each result I plan to claim, I need proof. Examples:

- A screenshot of the working output, dashboard or test results.
- A README file that explains the project.
- A link to the code or files.
- The dataset or a description of where the data came from (if I am allowed to share it).

If I cannot show evidence for a claim, I remove the claim.

### Step 4: Take screenshots

- Take clear screenshots that show real work.
- Show the output, not just the setup.
- Check that no private or sensitive information is visible.
- Give each file a simple name, for example `project-name-dashboard.png`.
- Add a short caption saying what the screenshot shows.
- Add alt text so the image makes sense without seeing it.

### Step 5: Add project links

- Link to the GitHub repository (or where the files are stored).
- Check that the link opens when I am logged out.
- Make sure the README is up to date and matches the case study.
- Link to a live version or a report only if one really exists.

### Step 6: Write the case study

- Copy the template below.
- Fill in the three sections using my notes and evidence.
- Read it out loud. If it sounds unnatural, I simplify it.
- Remove any word or claim I cannot back up.

### Step 7: Add it to the Projects page

- Add a short summary card on the Projects / Case Studies page. It should include the title, one sentence about the problem, the tools used and a link to the full case study.
- Put the full case study on its own section or page.
- Keep the format the same as my earlier case studies.

### Step 8: Update the rest of my portfolio

- Home: update the skills list only if I really used a new skill in this project.
- About Me: add to my learning journey if the project taught me something important.
- Contact: check that my email and LinkedIn links still work.

### Step 9: Final check before publishing

- [ ] Every statement is true.
- [ ] Every result has evidence.
- [ ] Unfinished work is clearly marked as unfinished.
- [ ] Screenshots are clear and have captions.
- [ ] All links work.
- [ ] The tools listed are the tools I really used.
- [ ] The tone matches my other case studies.
- [ ] Spelling and grammar are checked.

## Example From My Existing Work: Task API

This is a short example of how the three sections work, using only facts from my Task API project.



**Problem:** I wanted to understand how APIs work and how to do basic CRUD operations (create, view, update and delete) using Python.



**What I Did:** I built a small application for managing tasks. I used Python and FastAPI, with Uvicorn as the server. Tasks are stored in an in-memory Python list, not a database, so they reset when the server restarts. I used Git to track changes. On my first commit, Git showed an error because my name and email were not set up. I fixed this by setting my Git username and email in Command Prompt.



**What Came Out of It:** All four CRUD operations work. I wrote 12 automated tests with pytest. All 12 passed, with one deprecation warning from the testing dependencies. I wrote a README and have a Swagger screenshot as evidence. I learned how APIs let applications share information, how to set up a Python project, and how to use Command Prompt and Git. I am still improving my understanding of how CRUD operations work and how to choose better project structure and names.
